## Prediction as a SQL primitive

`forecast()`, `detect_anomalies()`, and `predict()` become functions you call
over your own rows: `forecast` and `detect_anomalies` are aggregates that
compose with `WHERE`, joins, and `GROUP BY`; `predict` is a scalar that composes
with row-level `SELECT`, `WHERE`, and joins, so ORMs and query builders work
unchanged. The core is one small C99 file with no
dependencies, so it runs in your app, on a phone, in the browser, or in the
per-database state an AI agent keeps.

```sql
-- forecast a metric 24 steps ahead: plain SQL supplies the rows
SELECT forecast(ts, value, 24) FROM readings;

-- GROUP BY splits the series. WHERE, joins, and bound parameters
-- compose, so ORMs and query builders work unchanged.
SELECT city, forecast(ts, value, 24) FROM readings GROUP BY city;

-- and when a stronger model is too heavy to call per query:
-- distill it once into a few-KB native student that lives in your
-- database, then serve the student in microseconds
SELECT model_id FROM distill_forecast('SELECT * FROM windows',
  '{"context":96,"horizon":24,"student_id":"traffic-v1"}');
SELECT forecast(ts, value, 24, '{"model":"traffic-v1"}') FROM readings;
```

## The pipeline, the meter, or a SQL function

Every way to predict on tables makes you pick one: build the pipeline,
pay the meter, or call a function where the data already lives.

The honest asterisk: a frontier model called zero-shot is still the accuracy
ceiling. The [benchmarks](./benchmarks/) measure the gap; a distilled student
typically gives up about half a point of accuracy against its teacher.

:::caution[Pre-1.0]
The SQL surface and option keys may change between minor versions, and the
changelog documents every break. Your data outlives the churn: stored
students and the model registry use versioned on-disk formats that stay
servable across upgrades, and migrations are idempotent.
:::
